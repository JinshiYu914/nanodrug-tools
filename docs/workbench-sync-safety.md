# 实验工作台多端数据同步设计

本文记录 tLNP、IVT mRNA 与配方筛选三个自动保存工作台的同步模型。目标不是在浏览器之间自动合并 JSON，而是在网络中断、旧设备再次上线和并发编辑时，保证云端记录与本机草稿都不会被静默覆盖。

## 1. 适用范围

同步控制层仅处理以下 `lnp_saved_items.type`：

- `tlnp_experiment`
- `ivt_batch`
- `screening_session`

配方库、RiboGreen 显式记录、抗体库和 CL-4B 柱预设仍沿用显式保存流程。访客 tLNP 示例完全在 React 内存中运行，不进入本同步系统。

## 2. 根因与设计原则

旧实现打开记录后直接使用侧栏携带的 JSON 初始化编辑器，并在状态变化后整条覆盖云端。新设备上的空白状态、旧侧栏快照或解析后的默认值都可能触发写入，覆盖另一设备已经保存的内容。

新设计遵循四条原则：

1. **打开时云端优先。** 侧栏记录只用于定位 ID；选择记录后必须再次请求云端正文。
2. **没有版本基线就不写。** 读取、解析、迁移旧 JSON 和初始化默认值都不会标记为编辑。
3. **本机修改先成为草稿。** 草稿按用户、记录类型和记录 ID 隔离保存在 IndexedDB。
4. **冲突保留两份。** 不做不可靠的逐字段自动合并；云端原记录保持不变，本机内容创建为同目录冲突副本。

## 3. 数据版本与条件写入

迁移 `supabase/migrations/008_workbench_sync_safety.sql` 为 `lnp_saved_items` 增加：

```text
data_revision BIGINT NOT NULL DEFAULT 1
```

数据库触发器负责：

- `data` 真正变化时递增 `data_revision`；
- 所有 UPDATE 统一由服务端刷新 `updated_at`；
- 重命名、移动和排序不递增数据版本，避免产生与正文无关的假冲突。

自动保存调用：

```text
UPDATE lnp_saved_items
SET data = 本机草稿
WHERE id = 记录ID
  AND data_revision = 打开时版本
RETURNING *
```

返回一行表示写入成功，并用返回的完整记录建立下一版基线；返回零行表示记录已被其他设备更新或删除，进入冲突处理。

## 4. IndexedDB 草稿结构

数据库名为 `lnp-partner-workbench-cache`，缓存键为：

```text
userId:type:itemId
```

每条缓存保存：

- 最近一次记录元数据及 JSON 正文；
- 草稿所基于的 `baseRevision`；
- `dirty`，表示是否有尚未同步的本机修改；
- `localUpdatedAt`，用于故障排查和离线列表排序。

不同账户的数据不能互相读取。用户显式退出登录时删除该用户三个工作台的缓存。

## 5. 打开记录

```text
用户选择记录
    │
    ├─ 请求云端成功
    │    ├─ 无本机草稿 → 采用云端
    │    ├─ 草稿基线 = 云端版本 → 恢复本机草稿，等待同步
    │    └─ 草稿基线 ≠ 云端版本 → 创建冲突副本
    │
    └─ 请求云端失败
         ├─ 有本机缓存 → 离线打开
         └─ 无本机缓存 → 显示失败，不初始化并写回空白记录
```

侧栏拉取成功时会更新干净缓存，但永远不会覆盖 `dirty` 草稿。云端已删除的干净缓存会清除；仍有本机修改的缓存继续显示，以便恢复为冲突副本。

## 6. 编辑与自动保存

只有编辑器显式调用 `update()` 才会产生草稿。流程如下：

1. 更新 React 状态；
2. 立即把草稿写入 IndexedDB；
3. 显示“本机草稿待同步”；
4. 停止编辑约 800 ms 后，以当前 `baseRevision` 条件写回云端；
5. 成功后更新版本基线、缓存完整云端记录并显示“已同步”。

若一次保存尚未完成时又发生编辑，新修改继续保留。第一次请求成功后，新草稿使用服务端返回的新 revision 再次保存，不会因请求时序丢失最后一次输入。

## 7. 离线恢复与冲突副本

已有缓存的记录可以离线打开和编辑；新建实验、文件夹及首次从未缓存的记录仍要求联网。浏览器触发 `online`、页面重新聚焦或 Supabase Realtime 通知时重新核对云端。

恢复联网后：

- 云端版本仍等于草稿基线：自动上传原记录并清除 `dirty`；
- 云端版本已变化：保留云端原记录，并以本机完整 JSON 创建“原名称（冲突副本 MM-DD HHmm）”；
- 原记录被删除：同样创建冲突副本；
- 原目录也被删除：在根目录创建冲突副本；
- 副本创建失败：保留 IndexedDB 草稿并继续显示待同步，不丢弃本机内容。

冲突副本是完整工作台记录，不尝试逐字段合并。用户可以对照两份内容后决定保留、重命名或删除哪一份。

## 8. Realtime 与页面恢复

三个工作台监听当前用户的 `lnp_saved_items` 实时变化，并在浏览器重新联网或页面重新获得焦点时主动复核：

- 没有本机修改：直接采用云端新版；
- 有本机修改且版本未变：继续上传草稿；
- 有本机修改且版本变化：创建冲突副本。

实时消息仅作为“需要重新读取”的信号，最终内容仍从 Supabase 重新获取，避免直接信任不完整或乱序的事件 payload。

## 9. 状态显示

所有工作台共用以下状态：

| 状态 | 含义 |
|---|---|
| 正在拉取云端 | 正在建立可信版本基线，禁止自动保存 |
| 已同步 | 当前正文与云端版本一致 |
| 本机草稿待同步 | 已保存到 IndexedDB，尚未成功写回云端 |
| 已生成冲突副本 | 云端和本机内容均已保留，当前已切换到副本 |
| 同步失败 | 请求失败，但本机草稿仍保留 |

## 10. tLNP 访客示例边界

未登录访问 `/tools/tlnp` 时使用一份明确标注为虚构、非实验建议的 anti-CD3 四模块示例：

- 允许编辑、增删、切换模块、查看总览和导出 PDF/Excel/JSON；
- 状态只存在于当前 React 组件内，刷新即恢复初始示例；
- 不调用 Supabase，也不打开 IndexedDB；
- 新建实验、实验库、抗体/柱预设库、跨批次比较及 RiboGreen 云端往返均要求登录。

## 11. 抗体快照

`ProteinEntry` 的来源、表达载体、表达日期和备注与抗体其余信息一起写入批次 JSON。抗体库只用于复制初始值，批次始终持有不可追溯更新的快照：以后修改或删除抗体库条目，不会改写历史实验记录。

旧批次缺失新增字段时解析为空字符串；重新保存、总览、PDF、Excel和跨批次比较均使用同一个批次快照。

## 12. 运维与验收

部署新代码前必须手动在 Supabase 执行 `008_workbench_sync_safety.sql`。未执行迁移时，客户端会保留本机草稿并提示迁移文件，不应反复尝试无版本保护的覆盖写入。

发布前至少验证：

1. A、B 两个独立登录会话打开同一记录；A 保存后，B 重新打开应先看到 A 的云端最新版。
2. A、B 基于同一 revision 分别编辑；先保存的一端更新原记录，后一端生成冲突副本。
3. 已缓存记录断网编辑、刷新、恢复联网；云端未变化时自动同步。
4. 云端读取失败或记录被删除时，空白默认值不产生写请求。
5. 访客编辑后刷新恢复示例，浏览器网络和存储面板中没有 Supabase/IndexedDB 写入。
