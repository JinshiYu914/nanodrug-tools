# 实验工作台多端数据同步设计

本文记录 tLNP、IVT mRNA 与配方筛选三个手动云端保存工作台的同步模型。编辑会自动形成 IndexedDB 本机草稿，只有用户点击“保存到云端”或按 `⌘/Ctrl + S` 才写 Supabase。目标不是在浏览器之间自动合并 JSON，而是在网络中断、旧设备再次上线和并发编辑时，保证云端记录与本机草稿都不会被静默覆盖。

## 1. 适用范围

同步控制层仅处理以下 `lnp_saved_items.type`：

- `tlnp_experiment`
- `ivt_batch`
- `screening_session`

配方库、RiboGreen 显式记录、抗体库和 CL-4B 柱预设仍沿用显式保存流程。访客 tLNP 示例完全在 React 内存中运行，不进入本同步系统。

## 2. 根因与设计原则

旧实现打开记录后直接使用侧栏携带的 JSON 初始化编辑器，并在状态变化后整条覆盖云端。新设备上的空白状态、旧侧栏快照或解析后的默认值都可能触发写入，覆盖另一设备已经保存的内容。

新设计遵循四条原则：

1. **打开时云端优先。** 侧栏记录只用于定位 ID；选择记录后必须再次请求云端正文。
2. **没有版本基线就不写。** 读取、解析、迁移旧 JSON 和初始化默认值都不会标记为编辑。
3. **本机修改先成为草稿。** 草稿按用户、记录类型和记录 ID 隔离保存在 IndexedDB。
4. **冲突保留两份。** 不做不可靠的逐字段自动合并；云端原记录保持不变，本机内容创建为同目录冲突副本。

## 3. 数据版本与条件写入

迁移 `supabase/migrations/008_workbench_sync_safety.sql` 为 `lnp_saved_items` 增加：

```text
data_revision BIGINT NOT NULL DEFAULT 1
```

数据库触发器负责：

- `data` 真正变化时递增 `data_revision`；
- 所有 UPDATE 统一由服务端刷新 `updated_at`；
- 重命名、移动和排序不递增数据版本，避免产生与正文无关的假冲突。

手动保存调用：

```text
UPDATE lnp_saved_items
SET data = 本机草稿
WHERE id = 记录ID
  AND data_revision = 打开时版本
RETURNING id, user_id, project_id, last_modified_by, type, is_folder,
          parent_id, name, sort_order, created_at, updated_at, data_revision
```

返回一行表示写入成功，并用返回的元数据建立下一版基线；刚刚提交的 JSON 已在本机内存中，不要求数据库再返回一遍。返回零行表示记录已被其他设备更新或删除，进入冲突处理。

## 4. IndexedDB 草稿结构

数据库名为 `lnp-partner-workbench-cache`，缓存键为：

```text
userId:scope:type:itemId
```

每条缓存保存：

- 最近一次记录元数据及 JSON 正文；
- 草稿所基于的 `baseRevision`；
- `dirty`，表示是否有尚未同步的本机修改；
- `localUpdatedAt`，用于故障排查和离线列表排序。

不同账户的数据不能互相读取。用户显式退出登录时删除该用户三个工作台的缓存。

## 5. 打开记录

```text
用户选择记录
    │
    ├─ 请求云端成功
    │    ├─ 无本机草稿 → 采用云端
    │    ├─ 草稿基线 = 云端版本 → 恢复本机草稿，等待手动保存
    │    └─ 草稿基线 ≠ 云端版本 → 保留本机草稿，手动保存时创建冲突副本
    │
    └─ 请求云端失败
         ├─ 有本机缓存 → 离线打开
         └─ 无本机缓存 → 显示失败，不初始化并写回空白记录
```

侧栏只读取不含 `data` 的轻量摘要，不再为所有记录预取完整 JSON。选中记录后才按 ID 读取正文。云端已删除的干净缓存会清除；仍有本机修改的缓存继续显示，以便恢复为冲突副本。未曾在本机打开过的记录离线时不可载入。

## 6. 编辑、本机草稿与手动云端保存

只有编辑器显式调用 `update()` 才会产生草稿。流程如下：

1. 更新 React 状态；
2. 立即把草稿写入 IndexedDB；
3. 显示“本机草稿，尚未保存到云端”；
4. 用户点击“保存到云端”或按 `⌘/Ctrl + S` 后，以当前 `baseRevision` 条件写回云端；
5. 成功后更新版本基线、清除 `dirty` 并显示“已保存”。

若一次保存尚未完成时又发生编辑，新修改继续保留为本机草稿，不会在后台自动发起第二次请求；用户可在第一次保存结束后再次保存。切换记录前会提示尚未保存，但允许保留草稿后切换。关闭或刷新页面时浏览器会提示，同时草稿继续留在 IndexedDB。

## 7. 离线恢复与冲突副本

已有缓存的记录可以离线打开和编辑；新建实验、文件夹及首次从未缓存的记录仍要求联网。浏览器重新联网、页面重新聚焦时不会自动读取或写入云端。

恢复联网后不会自动上传。用户手动保存时：

- 云端版本仍等于草稿基线：上传原记录并清除 `dirty`；
- 云端版本已变化：保留云端原记录，并以本机完整 JSON 创建“原名称（冲突副本 MM-DD HHmm）”；
- 原记录被删除：同样创建冲突副本；
- 原目录也被删除：在根目录创建冲突副本；
- 副本创建失败：保留 IndexedDB 草稿并继续显示待同步，不丢弃本机内容。

冲突副本是完整工作台记录，不尝试逐字段合并。用户可以对照两份内容后决定保留、重命名或删除哪一份。

## 8. 手动从云端重新加载

工作台长期关闭 Realtime，也不监听浏览器重新联网或页面重新获得焦点事件。客户端不会建立工作台 Broadcast/Postgres Changes 频道；数据库迁移 `016_disable_workbench_broadcast.sql` 会删除 014/015 添加的触发器、函数和 `realtime.messages` 策略。

云端正文只在以下动作读取：

- 首次打开或切换记录；
- 用户刷新整个页面并恢复当前记录；
- 用户点击“从云端重新加载”。

主动重新加载当前记录时：

- 没有本机修改：直接以云端版本替换当前内容和干净缓存；
- 有本机草稿：先确认是否放弃草稿，用户取消则不发起覆盖；
- 请求失败：保留当前内容和 IndexedDB 草稿；
- 请求期间又发生编辑：不采用迟到的云端响应，保留新草稿；
- 云端记录已删除：干净缓存清除；有草稿时仍保留草稿。

多终端之间不会自动刷新。另一终端保存后，本终端要通过上述读取动作才能看到新版本；如果本终端已基于旧版本编辑，手动保存仍由 CAS 检出冲突并创建副本。

## 9. 状态显示

所有工作台共用以下状态：

| 状态 | 含义 |
|---|---|
| 正在拉取云端 | 正在建立可信版本基线，禁止云端保存 |
| 已保存 | 当前正文与云端版本一致 |
| 本机草稿，尚未保存到云端 | 已保存到 IndexedDB，等待用户手动保存 |
| 已生成冲突副本 | 云端和本机内容均已保留，当前已切换到副本 |
| 保存失败 | 请求失败，但本机草稿仍保留 |

## 10. tLNP 访客示例边界

未登录访问 `/tools/tlnp` 时使用一份明确标注为虚构、非实验建议的 anti-CD3 四模块示例：

- 允许编辑、增删、切换模块、查看总览和导出 PDF/Excel/JSON；
- 状态只存在于当前 React 组件内，刷新即恢复初始示例；
- 不调用 Supabase，也不打开 IndexedDB；
- 新建实验、实验库、抗体/柱预设库、跨批次比较及 RiboGreen 云端往返均要求登录。

## 11. 抗体快照

`ProteinEntry` 的来源、表达载体、表达日期和备注与抗体其余信息一起写入批次 JSON。抗体库只用于复制初始值，批次始终持有不可追溯更新的快照：以后修改或删除抗体库条目，不会改写历史实验记录。

旧批次缺失新增字段时解析为空字符串；重新保存、总览、PDF、Excel和跨批次比较均使用同一个批次快照。

## 12. 运维与验收

部署新代码前必须确认 Supabase 已执行 `008_workbench_sync_safety.sql`。Disk IO Budget 恢复后，在低流量窗口手动执行 `013_lnp_saved_items_io_indexes.sql`。已执行过 014/015 的项目需再执行 `016_disable_workbench_broadcast.sql`，并删除或继续不设置 `NEXT_PUBLIC_WORKBENCH_REALTIME_ENABLED`；新前端不再读取该变量。未执行版本迁移时，客户端会保留本机草稿并提示迁移文件，不应反复尝试无版本保护的覆盖写入。

发布前至少验证：

1. A、B 两个独立登录会话打开同一记录；A 保存后，B 保持原内容，点击“从云端重新加载”或刷新页面后看到 A 的云端最新版。
2. A、B 基于同一 revision 分别编辑；先保存的一端更新原记录，后一端生成冲突副本。
3. 已缓存记录断网编辑、刷新、恢复联网；恢复后不自动读取或上传，点击保存才更新云端。
4. 云端读取失败或记录被删除时，空白默认值不产生写请求。
5. 连续编辑期间没有 Supabase PATCH；一次手动保存只产生一次 PATCH，且不触发侧栏全量正文读取。
6. 访客编辑后刷新恢复示例，浏览器网络和存储面板中没有 Supabase/IndexedDB 写入。
7. 页面切到后台再回来、网络离线再恢复时没有工作台云端读取，也没有 Realtime WebSocket/频道。
8. 有本机草稿时点击“从云端重新加载”会先确认；取消后草稿不变，请求失败时草稿仍在。
